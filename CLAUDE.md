# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Single-school Montessori preschool app. Vanilla ES modules, **no build step, no npm dependencies**. Two entry points share one codebase: root `index.html` is the public demo (fake data in `localStorage`, persona switcher, GitHub Pages); `app/index.html` is the real app (Supabase backend, Razorpay test mode). `README.md` is the detailed technical reference; `docs/GO-LIVE.md` is the user's click-by-click cloud setup.

## Commands

```sh
npm run serve                          # static server, default port 8080 (demo at /, real app at /app/)
node scripts/serve.mjs 8090            # port 8080 is often taken on this machine by an SSH tunnel
npm test                               # node --test "tests/*.test.mjs" (demo-mode + domain + import tests)
node --test tests/fees.test.mjs        # one file
node --test --test-name-pattern="#17" "tests/*.test.mjs"   # one test by name
npm run scan                           # fake-data / real-name / secrets / network-call scan; exits 1 on any hit
npm run check-domain                   # fails if supabase/functions/_shared copies drifted from src/domain, or permissions.test.sql from the matrix
```

Backend (Docker via Colima + Supabase CLI; all local, fake data, local test secrets in gitignored `supabase/.env.local`):

```sh
supabase start && supabase db reset    # migrations + generated supabase/seed.sql
node scripts/mock-razorpay.mjs --write-env   # once: invent local gateway/webhook secrets
npm run functions                      # supabase functions serve --env-file supabase/.env.local
npm run test:db                        # supabase db reset + pgTAP (supabase/tests/rls.test.sql: RLS matrix, ledger guards)
npm run test:supabase                  # Edge Function HTTP + realtime tests (needs `npm run functions` running)
npm run e2e                            # money + photo scenarios through the functions → reconcile() + SQL second path
```

Full acceptance order: `npm test`, `npm run scan`, `npm run check-domain`, then `npm run test:db` **first** (the function suites and e2e pay invoices; on a used database they fail with "no open invoice"), `npm run test:supabase`, `npm run e2e`. `tests-supabase/admin.test.mjs` runs first: it enrols the principal in two-step and removes the authenticator (and resets the policy) in `after()`; if it is interrupted, remove the principal's factor (Studio > Auth, or `delete from auth.mfa_factors`) before rerunning the other suites. The test files start the mock Razorpay server on 54399 themselves: never start another copy (a second listener makes the suites hang). `supabase functions serve` dies when the database is reset under it or when a background shell hits its 2-hour limit; restart it with `npm run functions`.

Local sign-ins are `principal@ teacher-pa@ accountant@ driver1@ parent-siblings@ parent-bus@example.com`; the OTP arrives in Mailpit (http://127.0.0.1:54324). Docker reaches the host mock gateway at `http://host.lima.internal:54399`. For `/app/` locally, put the local URL + anon key in gitignored `app/config.local.js`.

## Regenerate after editing

- `src/domain/**` or `src/store/schema.js` → `npm run sync-domain` (Deno can't import `src/`; the Edge Functions run synced copies in `supabase/functions/_shared/`). **Never edit the copies.**
- `src/domain/permissions.js` (the permission matrix) → `npm run permissions-sql` (regenerates `supabase/tests/permissions.test.sql`; never edit it by hand).
- `src/seed/**`, `src/store/schema.js` or the curriculum starter list → `npm run seed-sql` (rebuilds `supabase/seed.sql`; consents come from `scripts/seed-sql.mjs`, demo photo rows are left out). The SQL seed is local-only: `supabase db push` never sends it to the cloud.
- **Database changes are forward-only**: 0001–0007 are applied to the school's cloud project, so never edit them; add the next numbered file under `supabase/migrations/`. A migration that replaces `persist`/`load_slice`/`my_snapshot` wraps the previous version (the pattern in 0004/0005), and pgTAP plan counts must be raised with new tests.
- **A new privacy-notice version** needs four changes together: `PRIVACY_VERSION` (`src/ui/privacy.js`), `CONSENT_VERSION` (`src/domain/commands.js`, then `npm run sync-domain`), a migration redefining `app.consent_version()`, and in that migration a refresh of every row of `photo_consent_flags` (they are kept by triggers and would otherwise judge photos against the old version).

## Architecture

- **Layers**: `src/domain/` pure functions (no DOM, no I/O) → `src/store/` (schema typedefs, demo localStorage adapter with commit/rev) → `src/api/` (the only data module screens may import) → `src/ui/` (shell, hash router, screens). Screens import `api` plus the `money`/`dates` display helpers only.
- **One implementation of every write**: `src/domain/commands.js` is the registry (`slice`, `authorize(persona, db, args)`, `run(db, args, ctx)`). The demo runs commands inside `storage.commit()`; the real app posts `{name, args}` to the `command` Edge Function, which runs the same registry: `public.load_slice` → role read from `app_users` (never JWT claims) → `authorize` → `run` → `public.persist(slice, expectedRev, changes)` in one transaction, retried on `CONFLICT`. This is what makes receipt/invoice numbers contiguous without a SEQUENCE. New writes go in the registry, not in `api/` or SQL.
- **Learning (Phase 3)**: collections `presentations, observations, photos, progressEvents, reports` (+ `consents` in the document, `students.leftOn`, `school.retention`); schema v2 with a real `migrate()` in `src/store/storage.js`. The demo's storage key is bumped (now `montessori.db.v3`, older keys removed on first load) whenever returning visitors must get new sample data, because `migrate()` only adds empty lists. Commands are slice `learning`. Observations are staff-only until `sharedAt`; parents never see progress except inside a published, frozen `reports` row. Photos are metadata rows; bytes are a Storage object (real app, signed URLs minted server-side) or an SVG illustration / IndexedDB blob (demo, `src/api/demo-photos.js`). The UI shows photos only through `URL.createObjectURL(blob)` from `api.photos.blob(id)`; never put a URL in the DOM. Photo consent is per child and strict: every guardian with live `app_account` consent must also hold live `photos` consent (`photoConsentFor`; in SQL the trigger-maintained `photo_consent_flags`, required by parent RLS and by `photos.viewUrl`). The `child-photos` bucket is private with no storage policies; uploads use a 2-hour single-path grant and Storage cannot revoke it, so `photosCleanup` (also in the 15-minute cron) deletes files of rejected/deleted/expired rows at once.
- **Mode is bound to the entry HTML**, never a runtime toggle: `src/api/index.js` exports the remote api when `window.__APP_CONFIG__` exists (set by `app/config.js`), else the demo api. `src/ui/**` and root `index.html` must never mention the app config, Supabase or `remote.js` (a test asserts it); UI checks `api.mode`.
- **Reads in the real app**: `public.my_snapshot()` (SECURITY INVOKER) returns the demo's `Db` shape filtered by RLS, so screens and domain read functions are identical in both modes. Tables store each entity as a JSONB `doc` plus generated key columns; sensitive fields live in separate tables (`student_health`, `staff_contacts`, `student_guardians`, `trip_state`, `trip_positions`).
- **RLS is the security boundary** (the anon key is public): `anon` gets nothing; `authenticated` is SELECT-only by role; `load_slice`/`persist` are service-role only; the only SECURITY DEFINER function is the sign-up trigger. pgTAP fails on any other definer function or a view without `security_invoker`. Since 0008 the definer list is exactly `app.link_new_auth_user` and `public.end_sessions` (service role only).
- **Payments**: amount always computed server-side from invoice balances; `pay-verify`, `rzp-webhook` and `pay-status` all funnel into the one idempotent `fees.recordGatewayPayment` (keyed on gateway payment id; webhook event ids stored once).
- **Administration** (schema v3, migration 0008): data-rights desk (`dataRequests`, slice `rights`), `school.announcement`, `people.updateGuardian` run as ordinary commands in both modes; account actions (`admin.blockUser`/`unblockUser`/`changeSignInEmail`/`noteAccountAction`, server only) are paired with the auth server's admin API by the `admin-accounts` function, which only an active principal with JWT `aal` = aal2 may call. Two-step rule in exactly two places: `twoStepRequired` (`src/domain/admin.js`, used by `persist.ts` → `TWO_STEP_REQUIRED` 403) and `app.two_step_ok` (SQL, inside `app.my_link()`, so every policy and `my_snapshot` → `status:'two_step_required'`); enrolment comes from `two_step_enrolled` (trigger on `auth.mfa_factors`), the school-wide switch from `app_policy` 'two_step'. Status `blocked` closes RLS and commands at once; `public.end_sessions` ends sessions and writes `session_cutoffs` (an access token with `iat` before the cutoff gets nothing from `app.my_link()`; `my_snapshot` says `session_ended` and the app signs that tab out); removing the last authenticator writes a cutoff too. The account commands are `functionOnly: 'admin-accounts'`: POST /command refuses them. The accountant reads every audit row except the account desk's (entity `appUser`). `sign_in_events` (trigger on `auth.users.last_sign_in_at`) is principal-only and pruned at 90 days. `whoCanSee` is built from `buildPersonas`/`consentScopedPersona`/`sees`; the permission matrix (`src/domain/permissions.js`): read rows are checked against the database (generated `permissions.test.sql`, pgTAP) and in JS; action rows against the registry's authorize (`tests/admin-domain`), and the teacher's and aal1 principal's denied actions against the command function (`tests-supabase/admin.test.mjs`). The desk's erasure requests go in_progress at anonymise and done only when `people.finishErasure` succeeds.
- **Transport**: driver posts fixes as `transport.recordPosition`; stop events are derived server-side by the domain hysteresis code; parents receive Realtime `postgres_changes` authorized by RLS and live `bus_live` consent.

## Invariants the tests and scan enforce

- Money is integer paise (`assertPaise`); display via `formatPaise` (Indian grouping). Percentages in basis points.
- Dates are `YYYY-MM-DD` strings parsed by regex; `Date.parse(` / `new Date(<string>)` in `src/domain` fails a lint test. Server code computes IST business dates with `dateInZone(ms, 330)` (Deno runs in UTC).
- Imports/transforms report counts that add up (`inputRows = ok + quarantined + duplicate`, holidays `= imported + skippedDuplicate + rejected`); rejected rows carry line + reason.
- Colours and fonts in `app.css` come from its `:root` tokens (the Kinfolk design system, `docs/DESIGN-SYSTEM.md`); add a token there, with its contrast, before using a new colour. Places that cannot read CSS variables repeat the hex values and must be kept in step: `src/ui/map.js` (route lines), `src/ui/screens/pay-online.js` (Razorpay theme), the `theme-color` meta in both HTML files, `app/manifest.webmanifest`; `src/ui/print.css` is black on white by design.
- Every interpolated value in UI templates goes through `esc()` (`src/ui/components.js`), numbers included.
- `fetch(` is allowed only in `src/api/remote*.js` and `src/api/supabase/**`. The only external script is Razorpay Checkout, loaded only on the real app's pay screen; supabase-js and Leaflet are vendored.
- Demo photos are drawn SVGs (`src/seed/illustrations.js`, materials only, numbers of at most three digits so the scan's phone/Aadhaar rules cannot match) or an IndexedDB blob; no binary image is committed outside `tests/fixtures/`. Curriculum names are generic material names.
- **Fake data only, public repo**: seed surnames must come from `FAKE_SURNAMES`, phones `+91-90000-00NNN`, emails `@example.com`. The previous vendor's name and domain must never appear in tracked files — the scan checks them by SHA-256 hash, so don't add them in plain text anywhere (including tests, comments, import-mapping presets). The school's own name, Kinfolk Montessori School, is used openly (owner's decision, 03-Oct-2026); the demo's people, addresses and money stay fake, its school name keeps "(Demo)", its fee heads say "(sample)", and every demo receipt carries a DEMO stamp.
- Local-only, gitignored files: planning records `PLAN.md`, `PLAN-PHASE2.md`, `PLAN-PHASE3.md`, `PLAN-REVIEW-LOG.md` (append-only audit/disposition log), `school-app-feature-list.md`; and the real school data for go-live, `first-run.json` / `first-run.sql` (`node scripts/first-run-sql.mjs first-run.json > first-run.sql`, pasted once into the cloud SQL Editor). Keep them out of git; they contain local paths, real names and emails. Don't read `first-run.json` beyond what a fix needs.
